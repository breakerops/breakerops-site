# Data-log additions

Three additive pieces that make the existing message chain usable by any model
provider. Nothing here changes live behavior; these are empty tables until the
backend jobs that fill them are built and approved.

## Why

The chain already exists: `inbound_messages` (raw, immutable) ->
`message_parses` (versioned interpretation) -> `outbound_drafts` (what Matt
replied, with sources and approval state). These tables close the loop:

1. **reply_feedback** - did the reply work, and what did the owner correct?
   A correction row stores the reply the owner WISHES had been sent. Over time
   this is the fine-tuning and few-shot source.
2. **doc_embeddings** - the retrieval index. At question time the backend
   pulls the right slice of the log for whatever provider is active in
   `model_providers`. Retrieval is the swappable layer, not training.
3. **eval_questions / eval_runs** - 30-50 real questions with known-right
   answers. Run them against each provider to see which model answers which
   kind of question best. That evidence is what a future per-question router
   should be built on, not guesses.

## Model-agnostic rules

- No provider names in table design. Providers live in `model_providers`;
  these tables reference them by name string only (`eval_runs.provider`).
- Every embedding row names its `embed_model`. Switching providers means
  re-embedding, not migrating.
- The hard rules stay in code, not in any model.

## Privacy

- Every row is partitioned by `business_id`; one shop's data never enters
  another shop's context.
- Embeddings are generated by the SAME provider already handling that shop's
  texts. No customer data goes anywhere new.
- `sms_opt_outs` is honored before any outbound use of this data.
- Eval and fine-tuning exports use approved `outbound_drafts` only, never raw
  customer chatter.

## Deploy

Apply `schema.sql` in the Supabase SQL editor (idempotent). Requires the
`vector` extension, which the script enables.
