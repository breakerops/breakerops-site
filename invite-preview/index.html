This example is intended for buddy@example.com. The shareable admission link alone does not grant access.

  1. Open the invitation.
  2. Verify the invited email through a separate email challenge.
  3. The server checks that the link is still valid and unused.
  4. Create a separate business account. Never join the inviter's private workspace.

What the backend must enforce
  • Only an active customer may request a link; only Jake may set allowances.
  • Allowance check and reservation happen in one transaction, so concurrent requests cannot overspend it.
  • Store a token hash, not the raw invitation link. Check expiry and revocation server-side.
  • One recipient, one use. A verified account must match the invited email in the recommended mode.
  • Revoked or expired unused links release the reserved allowance. Accepted links count as used.
  • Public requests never grant membership. Existing users keep access.
  • Matt must check active admission before handling work when inbound texting is connected.

Chosen: five invites, one use, tied to the buddy's email. Still to decide: expiry and activation details. No policy is activated by this preview.
